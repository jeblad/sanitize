# Agent notes for sanitize

## Comment convention

Signature comments use Doxygen-style `@`-tags: `@brief`, `@tparam`, `@param`,
`@return`, `@throws`. Settled from the existing code in `sanitize.hpp.in`,
which already uses this convention throughout. English only.

Edit `sanitize.hpp.in`, never `include/sanitize/sanitize.hpp` directly — the
latter is generated by CMake from the former (see `.aiexclude`).

## Code-review standards (rework-code)

Two standards apply to this project's C++ source:

1. Boswell, Dustin, and Trevor Foucher. *The Art of Readable Code*.
   O'Reilly Media, 2011. — base standard.
2. Holzmann, Gerard J. "The Power of Ten: Rules for Developing
   Safety-Critical Code." *IEEE Computer*, June 2006. — stricter overlay,
   applied because `decode_utf8`/`encode_utf8` do security-relevant UTF-8
   parsing even though the library as a whole isn't flight/medical/embedded
   safety-critical.

Composition: "The Art of Readable Code" is the base; "The Power of Ten"
narrows it further. Where the two disagree, the stricter reading (Power of
Ten) wins. No known unresolvable conflict between them has been found yet.

Project-specific rule exception:

- **Never use `assert`/abort-based checks (departs from Power of Ten Rule
  5).** This library is meant to embed in continuously-running programs, so
  an aborted process is itself an unacceptable failure mode, not a safe
  fallback. Every error condition must be reported (a return status or an
  exception, matching whatever the surrounding function already uses) or
  made structurally unreachable — never asserted-and-aborted. Example:
  `decode_utf8`'s empty-span case reports `Utf8Status::Invalid` rather than
  asserting non-empty input.

- **`decode_utf8` is left over Power of Ten Rule 4's ~60-line guideline and
  `.clang-tidy`'s cognitive-complexity threshold (76 lines, complexity 28
  against clang-tidy's own default threshold of 25; `.clang-tidy` itself is
  left at that default, not raised to accommodate this).** Splitting it was
  tried and rejected: the function's four lead-byte branches are each
  obviously correct by structural omission — the 2-byte branch has no
  surrogate/max-range check because there's no line there to have one, so a
  reader never has to wonder whether it's needed. Extracting that check into
  a shared helper makes it run unconditionally for every branch, correct
  only because of a numeric fact (2-byte codepoints top out at U+07FF,
  3-byte at U+FFFF, both below the surrogate/max-range danger zones) that a
  reader then has to verify by arithmetic instead of seeing structurally.
  For a function that already had one real overlong-surrogate-bypass bug,
  trading "obviously correct" for "correct if you check the math" is a
  worse deal than the line count implies. `decode_utf8` carries
  `// NOLINTNEXTLINE(readability-function-cognitive-complexity)`
  accordingly. A separate, low-cost extraction (a `has_valid_continuation`
  helper for the repeated structural-byte checks) was also considered and
  rejected for a different reason: it only trims the function by ~2 lines,
  not enough to matter, since the doc comment the new helper would need
  costs more lines elsewhere than it saves here.
